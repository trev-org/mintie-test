## Overview

Webhooks let your services react to identity events in near real time. Mintie
delivers each subscribed event as a signed HTTPS `POST` to your endpoint.
Payloads are versioned (`v1`) and use the same shape as the [audit log](/security/audit-logs)
export, so parsers written for audit export can consume webhook events without
modification.

Typical automations:

- Kick off an offboarding checklist when SCIM deactivates a user.
- Alert on first SSO sign-in from a new user.
- Sync provisioning events into an internal system of record.

## Create an endpoint

Webhooks are configured per organization at **Settings → Auth → Webhooks**.

<Steps>
  <Step title="Add an endpoint">
    Enter the destination URL (HTTPS only) and pick which event kinds to
    subscribe to. Leave the filter empty to receive every event.
  </Step>
  <Step title="Copy the signing secret">
    Mintie generates a signing secret when the endpoint is created. Store it
    in your secrets manager; you will use it to verify signatures.
  </Step>
  <Step title="Verify with a test fire">
    Use the **Send sample event** button to deliver a `webhook.test` event to
    the endpoint. The delivery log shows the response code and body.
  </Step>
</Steps>

Creating, editing, disabling, or rotating the secret on a webhook endpoint is
a sensitive action. Mintie requires step-up MFA before applying the change,
and the change itself is written to the audit log.

## Payload format

Every delivery has the same envelope:

```json
{
  "id": "evt_01j9x7c4pk",
  "version": "v1",
  "type": "scim.user.deactivated",
  "occurredAt": "2026-08-20T20:48:01.423Z",
  "orgId": "org_01j9x3wq8e",
  "data": {
    "userId": "user_01j9x5b2kd",
    "email": "jamie@acme.com",
    "connectionId": "conn_01j9x3wq8e"
  }
}
```

The `type` field matches the `AuditEventKind` values documented in the
[audit log event table](/security/audit-logs). The `data` object shape is
specific to each event type. See the AsyncAPI reference under the
**References** tab for the full schema of every event.

## Verify signatures

Every request carries two headers:

| Header | Value |
| --- | --- |
| `Mintie-Signature` | Hex-encoded HMAC-SHA256 of `{timestamp}.{raw_body}` using the endpoint secret |
| `Mintie-Timestamp` | Unix seconds when Mintie generated the signature |

Verify both the signature and the timestamp before trusting the payload.
Reject requests where the timestamp is more than 5 minutes off from your
server clock to prevent replay.

```ts Node.js
import { createHmac, timingSafeEqual } from "node:crypto";

const MAX_SKEW_SECONDS = 5 * 60;

export function verifyMintieWebhook(
  rawBody: string,
  signatureHeader: string,
  timestampHeader: string,
  secret: string,
): boolean {
  const timestamp = Number(timestampHeader);
  if (!Number.isFinite(timestamp)) return false;

  const skew = Math.abs(Math.floor(Date.now() / 1000) - timestamp);
  if (skew > MAX_SKEW_SECONDS) return false;

  const expected = createHmac("sha256", secret)
    .update(`${timestampHeader}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(signatureHeader, "hex");
  if (a.length !== b.length) return false;

  return timingSafeEqual(a, b);
}
```

<Warning>
  Verify against the raw request body, before any JSON parsing or
  re-serialization. Reordering keys or changing whitespace invalidates the
  signature.
</Warning>

## Delivery and retries

Mintie attempts each delivery at least once. An endpoint is considered
successful when it returns a `2xx` response within 10 seconds.

Failed deliveries retry with exponential backoff at 30s, 2m, 10m, 1h, and 6h.
After the last attempt, the delivery is marked failed in the log and no
further automatic retries occur.

<Info>
  Because delivery is at-least-once, your handler must be idempotent. Use the
  event `id` field as an idempotency key.
</Info>

## Delivery log

**Settings → Auth → Webhooks → Deliveries** lists every attempted delivery,
including:

- Event `id`, `type`, and timestamp
- HTTP response code, response body (first 4 KB), and latency
- Retry count and next scheduled retry, if any

Admins can redeliver any event manually from the log — useful when a
downstream service was briefly down or when you need to replay events after
fixing a handler bug.

## Event catalog

The event kinds you can subscribe to match the audit log taxonomy. See the
AsyncAPI reference under the **References** tab for full payload schemas.

| Event | Emitted when |
| --- | --- |
| `auth.signin.success` | User signs in (password or SSO) |
| `auth.signin.failure` | Sign-in fails |
| `auth.sso.linked` | Mintie user linked to an IdP identity |
| `auth.sso.unlinked` | Link removed by an admin |
| `auth.session.forced_relogin` | Session-migration job stamped a session |
| `scim.user.provisioned` | SCIM `POST /Users` succeeded |
| `scim.user.deactivated` | SCIM `DELETE /Users/{id}` succeeded |
| `apikey.created` | API key issued |
| `apikey.revoked` | API key revoked manually or by IdP deactivation |
| `webhook.test` | Test-fire from the admin UI |
