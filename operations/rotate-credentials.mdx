---
title: "Rotate credentials"
description: "Replace identity credentials without interrupting access"
---

Rotate credentials before they expire, after an administrator leaves, or whenever exposure is suspected. Treat an unplanned rotation as an incident and use the [incident-response runbook](/operations/incident-response).

## Inventory

| Credential | Stored or managed in | Validate with |
| --- | --- | --- |
| SAML signing certificate | Identity provider metadata | Test sign-in |
| OIDC client secret | IdP application and Mintie connection | Test sign-in |
| SCIM bearer token | IdP provisioning application and Mintie | Test-user lifecycle |
| Mintie API key | Calling application | One read-only API request |

Never place a secret value in a ticket, chat message, screenshot, or team runbook.

## Before any rotation

- Assign one person to update the IdP and another to validate Mintie.
- Record the credential owner, expiry, affected environment, and rollback window.
- Confirm an active administrator session is available.
- Pause unrelated changes until validation is complete.

## SAML signing certificate

1. Add or activate the new certificate in your IdP.
2. Refresh the metadata used by the Mintie connection. If self-service controls are unavailable, coordinate the update with Mintie support.
3. Run test sign-ins for an administrator and a standard member.
4. Retire the previous certificate only after both tests succeed.

<Tip>
  A metadata URL is easier to keep current than uploaded XML, but you should
  still test immediately after the IdP changes its active certificate.
</Tip>

## OIDC client secret

1. Create a replacement secret in the same OIDC application.
2. Update the Mintie connection with the new value.
3. Run **Test sign-in** in a private browser window.
4. Revoke the previous secret after the test succeeds.

If your IdP permits only one active secret, schedule a maintenance window and keep both administrators present.

## SCIM token

<Warning>
  SCIM token generation and rotation depend on the planned SCIM admin
  controls. Follow this sequence once those controls are available.
</Warning>

1. Generate a replacement token in **Settings → Auth → SSO → SCIM**.
2. Update the token in your IdP provisioning application.
3. Create or update one dedicated test user.
4. Revoke the previous token and confirm retries remain clear.

## API key

1. Create a replacement key under the correct user or service account.
2. Deploy it through your secret manager.
3. Verify one low-risk request in every affected environment.
4. Revoke the old key and monitor for `401` responses.

After the rotation, record who completed it, when the old credential was revoked, and the next planned rotation date—never the secret itself.
